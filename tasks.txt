 0. THE PROJECT IN ONE MINUTE
---------------------------------------------------------------------
Problem: in a microservices application it is hard to know WHICH
service is slow or failing. Goal: build a small microservices app,
make every service emit traces and metrics, send them through a Big
Data pipeline, and compute latency (p95), error rate, SLA, service
dependencies and anomalies, with alerts and a Grafana dashboard.
Everything starts with ONE command: docker compose up

Data path (everyone must be able to explain it):

 4-5 Flask/Spring microservices + load generator
    -> Kafka topics "traces" and "metriques"
    -> Data Lake BRONZE (raw JSON in MinIO)
    -> Lakehouse SILVER (Hudi table of calls: service, duration, status)
    -> Lakehouse GOLD (p95 latency + error rate per service, SLA,
       dependencies, anomalies)
    -> Grafana (latency, errors, call map, alerts)
 Airflow orchestrates the batch jobs. Docker Compose runs everything.

Good news for you: you are software engineers, so the microservices
part is your comfort zone. The new parts are Kafka, Hudi, Spark and
Airflow. Use your engineering strength to get points on quality
(clean code, tests, Docker, README, Git).

Link with your course (say it in the oral = extra credit):
  - Kafka partitions ~ HDFS blocks (data split to scale)
  - MinIO vs HDFS: both distributed storage
  - Spark DAG, lazy evaluation, narrow/wide transformations, shuffle
    (Chapter 4): show them in your jobs with df.explain()
  - Airflow is the modern replacement of Oozie (course ecosystem slide)
  - Hive/Spark SQL: SQL on big data

Why not Prometheus / Jaeger / OpenTelemetry? (the jury WILL ask)
  They are the industry standard tools for observability. Your
  project reproduces the data pipeline behind them with Big Data
  tools: durable storage of ALL traces, history, SQL analytics and
  machine learning at scale. Mention OpenTelemetry/W3C "traceparent"
  as the standard your span format is inspired by.

Version warning (most common failure):
  The Hudi "bundle" jar MUST match your Spark version (e.g. a
  hudi-spark3.5-bundle for Spark 3.5). Check Hudi's compatibility
  table in its docs and pin exact versions. Do not pick a Spark
  major version that Hudi does not list. Prefer apache/kafka (or
  confluentinc/cp-kafka) and apache/spark images; avoid Bitnami.

Computer warning: the whole stack needs about 8-12 GB RAM. Use
Docker profiles so each student starts only their part, one small
Spark worker (1-2 GB), limit WSL2 memory on Windows, and demo on the
strongest laptop (test it there early).

 4. THE MICROSERVICE APP AND THE DATA CONTRACT
---------------------------------------------------------------------
Mini e-commerce app (5 services, each with /health):

   client/load generator -> api-gateway (8000)
        gateway -> order-service  (POST /checkout)
        order   -> user-service    (GET /users/{id})
        order   -> product-service (GET /products/{id}, stock check)
        order   -> payment-service (POST /pay)

 Each service simulates realistic work: latency from a log-normal
 distribution (so p95 is very different from the average), small
 baseline error rate (~0.5%), and an admin endpoint:
   POST /admin/chaos {"latency_ms":800,"error_rate":0.3,"duration_s":120}
 It lets us inject faults on demand (this is how we demo anomalies).

TRACE PROPAGATION: the gateway creates trace_id; each service
receives headers X-Trace-Id, X-Parent-Span-Id, X-Caller-Service and
forwards them to the services it calls.

Kafka topic "traces": ONE span = ONE JSON message. Key = trace_id.
 {
  "trace_id":       "a3f9...",
  "span_id":        "91bc...",
  "parent_span_id": "77de...",     // null for the first span
  "service":        "payment-service",
  "caller_service": "order-service",
  "instance":       "payment-1",
  "version":        "1.0.0",
  "http_method":    "POST",
  "route":          "/pay",
  "status_code":    200,
  "status":         "OK",          // OK | ERROR
  "error_message":  null,
  "duration_ms":    134.2,
  "start_time":     "2026-11-20T14:00:01.120Z",
  "ingest_time":    "2026-11-20T14:00:01.300Z"
 }

Kafka topic "metriques" (every 10 s per service instance):
 { "service","instance","metric_time","cpu_percent","memory_mb",
   "requests_count","errors_count","in_flight" }

Other topics: "fault_events" (every injected fault with start/end and
type = our GROUND TRUTH to evaluate anomaly detection),
"alertes_obs" (alerts), "traces_dlq" (invalid messages, optional).

SILVER (Hudi):
 - spans: record key = span_id, precombine = ingest_time,
   partition = date(start_time). Upsert removes duplicates (Kafka is
   at-least-once; late/duplicate spans are normal).
 - metrics: record key = service + instance + metric_time.
GOLD (Student 3 defines the exact columns with 2 and 4):
 - service_latency_1min : service, window_start, count, error_rate,
   avg, p50, p95, p99
 - sla_daily            : service, day, % requests under the SLO,
   availability, SLO breached yes/no
 - service_dependencies : caller, callee, calls, avg latency, error rate
 - traces_summary       : trace_id, total duration, nb services,
   error flag, slowest service
 - anomalies            : service, window_start, score, type
 - alerts, fault_events
Put all of this in docs/data_contract.md. Any change = tell everyone.

 STUDENT 1 : MICROSERVICES + INSTRUMENTATION + KAFKA INGESTION
=====================================================================
Mission: build the application that produces the data, make it
observable, and push the data into Kafka reliably.
You own: services/, obs_lib/, the Kafka part of docker-compose.

A. LEARN FIRST (about 3-4 days)
 [ ] Kafka: topic, partition, offset, producer, consumer, consumer
     group, key, retention, at-least-once. Official quickstart with
     console producer/consumer.
 [ ] confluent-kafka Python producer (preferred; kafka-python is
     poorly maintained)
 [ ] Distributed tracing idea: trace, span, parent span, context
     propagation (read about OpenTelemetry / W3C traceparent)
 [ ] Python threading + queue (for non-blocking sending)

B. TASKS (in order)
 1. Agree with Students 2, 3, 4 on the contract (section 4).
 2. Kafka service in docker-compose (KRaft single broker) + Kafka UI;
    init step creating topics: traces (3 partitions), metriques,
    fault_events, alertes_obs, traces_dlq.
 3. Write obs_lib: a Flask middleware (before_request / after_request)
    that reads or creates trace headers, measures duration, builds
    the span JSON, and puts it in an in-memory queue. A background
    thread sends the queue to Kafka (batching, retries).
    ENGINEERING RULE: observability must never slow or break the
    service. If Kafka is down, the service keeps working (queue is
    bounded, extra spans are dropped and counted).
 4. A helper "traced_call(url)" that forwards X-Trace-Id,
    X-Parent-Span-Id and X-Caller-Service to downstream services.
 5. Metrics thread: every 10 s send cpu_percent, memory_mb (psutil),
    request/error counters, in-flight requests to "metriques".
 6. Build the 5 services (gateway, user, product, order, payment)
    with the call chain of section 4, realistic log-normal latency,
    baseline error rate, /health, config from environment variables,
    structured (JSON) logging.
 7. Chaos endpoint on every service: /admin/chaos (extra latency,
    error rate, full outage, duration). Each activation also sends a
    message to topic "fault_events" (service, type, start, end).
 8. Optional realism flag: resend ~1% of spans twice
    (--duplicate-rate) to prove at-least-once and later show Hudi
    deduplicating them.
 9. Validate spans before sending (required fields, duration >= 0);
    invalid ones go to traces_dlq.
10. Dockerfile for each service (small image, non-root user),
    compose service per microservice with profile "services".
11. pytest tests: middleware (span built correctly, headers
    propagated), chaos endpoint, producer queue when Kafka is down.
12. verify.py: small consumer that prints last messages (helps
    everyone debug). Document: README "Ingestion", Kafka UI
    screenshot, sequence diagram of one checkout request with spans,
    problems met (for the report).
13. Bonus: one service in Spring Boot; GitHub Actions running pytest.

C. DONE WHEN
 - 5 services start with compose and a checkout produces ~5 spans
   linked by trace_id/parent_span_id in Kafka UI
 - chaos injection visibly changes duration/status in messages
 - metrics arrive every 10 s

D. JURY QUESTIONS YOU MUST ANSWER
 - What is a trace vs a span? How is context propagated?
 - Why key = trace_id? Topic vs partition vs offset?
 - What if Kafka is down? (non-blocking queue, dropping policy)
 - At-least-once vs exactly-once; where do duplicates go?
 - Why custom instrumentation and not OpenTelemetry/Jaeger?
 - What overhead does instrumentation add?

E. PITFALLS
 - Kafka advertised listeners: containers use kafka:9092, your
   laptop another port. Understand it once.
 - Never send to Kafka synchronously inside the request.

 STUDENT 3 : SPARK PROCESSING + STREAMING + MLlib ANOMALIES
=====================================================================
Mission: turn spans and metrics into latency indicators, SLA,

You own: gold jobs, streaming alerts job, anomaly model scripts.

A. LEARN FIRST (about 4-5 days)
 [ ] PySpark DataFrames + Spark SQL (groupBy, join, window functions,
     percentile_approx) - practise on a sample of spans in a
     notebook, without Docker
 [ ] Course chapter 4: RDD, lazy evaluation, DAG, narrow vs wide
     transformations, shuffle, driver/executors
 [ ] Structured Streaming: readStream, trigger, checkpoint, event
     time, window, watermark, output modes
 [ ] MLlib: VectorAssembler, StandardScaler, KMeans, Pipeline
 [ ] Observability vocabulary: latency percentiles (p50/p95/p99),
     error rate, SLI/SLO/SLA, availability, error budget

B. TASKS (in order)
 1. Exploratory analysis of a sample of spans: latency distribution
    (average vs p95), error rate per service/route, rate per minute.
    Keep 3-4 charts for the report.
 2. Gold batch job gold_aggregates.py (from Silver):
    - service_latency_1min (count, error_rate, avg, p50, p95, p99
      using percentile_approx(duration_ms, 0.95))
    - service_dependencies (caller -> callee, calls, latency, errors)
    - traces_summary: rebuild each trace by grouping spans by
      trace_id (total duration, number of services, error flag,
      slowest service)
    - sla_daily: define an SLO (e.g. 95% of requests under 500 ms,
      availability 99%), compute % within SLO, availability, breach
 3. At least 5 Spark SQL queries kept in a file: slowest routes,
    services with highest error rate, p95 per hour, top 10 slowest
    traces, SLA breach list.
 4. Streaming job alerts_stream.py: read Kafka "traces", use event
    time + watermark, 1-minute windows per service; alert if p95 above
    the SLO or error rate above 5% for 2 consecutive windows; avoid
    alert spam (one alert per service per period). Write to Kafka
    "alertes_obs" and the Postgres alerts table. Thresholds in a
    config file. If percentile_approx gives trouble inside a streaming
    aggregation, compute it inside foreachBatch.
 5. Anomaly detection with MLlib:
    - Features per service and 1-minute window: avg latency, p95,
      error rate, request rate, cpu, memory (join metrics).
    - Normalize (StandardScaler); train KMeans on NORMAL periods;
      anomaly score = distance to nearest centroid; threshold =
      e.g. 99th percentile of training distances.
    - Baseline for comparison: simple z-score vs rolling mean/std.
    - EVALUATION with ground truth: join detected anomalies with the
      fault_events table; report precision, recall, detection delay
      for KMeans vs baseline. (Few teams can do this; it earns
      points and shows honesty.)
    - Save the model to s3a://models/anomaly/<version>.
 6. Scripts with arguments (dates, paths) so Airflow can call them:
    train_anomaly.py, detect_anomalies.py, gold_aggregates.py,
    gold_to_postgres.py (JDBC copy of Gold for Grafana, columns
    agreed with Student 4).
 7. Performance basics: spark.sql.shuffle.partitions small (e.g. 8)
    on a laptop; run df.explain() on one job and show the stages and
    the shuffle (link to the course).
 8. pytest tests on helper functions. Document: SLO definitions, p95
    method, model choice, metrics, limits.
